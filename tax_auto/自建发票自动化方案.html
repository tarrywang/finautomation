BUILD PLAN · 自建方案

自建电子税务局发票自动化

A pragmatic build plan: framework selection, model strategy,
architecture, and a 6-week roadmap to production.

TL;DR · 核心建议

不要用 agent framework,用 Playwright 写确定性脚本 + Claude 兜底

这是一个单一垂直场景(一个网站 · 一套固定流程 · 已知步骤), 不是开放任务。重型 agent framework(LangGraph / AutoGen / CrewAI)对你是负债不是资产—— 它们的价值在"动态规划",但你的流程是确定的。

推荐栈: Playwright (Python) + persistent Chromium profile + Claude Sonnet 4.6 vision 兜底。 90% 的步骤用确定性 selector 跑,10% 不稳定的步骤(改版、弹窗、二次扫脸触发)用 Claude 的视觉理解救场。模型只在看不懂页面时调用, 不进入主循环,API 成本每月几十块。

DECISION 01 · 框架选型

为什么不是 Browser-Use / 不是 LangGraph

Framework selection — why "less is more" for this workload

市场上能选的工具按"自主性"排成光谱,从纯确定性到纯自主:

工具 类型 适用场景 对你这个场景
Playwright 确定性框架 已知流程的网页自动化,稳定、快、可调试 ★ 主推——流程固定、跑得稳、token 零消耗
Computer Use
(Claude SDK)		 视觉 agent 无 selector 可用、桌面 GUI、需要"看图操作" 只用作兜底分支,不做主循环
Browser-Use LLM agent 开放任务("帮我订机票")、跨网站、未知 UI 过度——每步都过 LLM,慢且贵
Stagehand Playwright + AI 层 需要 AI 做元素识别,但仍想要 Playwright 控制力 合理备选,但相比纯 Playwright 增加依赖
LangGraph
AutoGen / CrewAI		 Agent 编排 多智能体协作、复杂规划、动态分支 完全过度——你不需要"智能体辩论"
八爪鱼/影刀 RPA 低代码 RPA 非开发者、Windows 桌面流程 不适合——你是开发者,且要跨 macOS
★ 主推方案

Playwright + Claude Sonnet 4.6 兜底

Deterministic-first, AI as fallback
✓流程是确定的。登录页 → 数字账户 → 全量发票查询 → 勾选 → 下载 → 轮询 ZIP,7 步全部已知。没有"agent 需要思考下一步是什么"。
✓Playwright 有 persistent context。用 launchPersistentContext() 把 cookies/storage 留在磁盘,人登录一次,脚本天天复用 session。
✓本地跑、零 API 费(主路径)。主流程不调 LLM。Claude 只在选择器失效、弹窗未知时调用——一个月几块到几十块。
✓可调试、可回放。Playwright trace viewer 可看每一步截图。生产事故复现成本极低。
✓跨平台。macOS / Linux / Windows 一份代码。你 Mac mini + MBP 双机部署没障碍。
✓未来可演化。需要时再叠 agent layer(给客户做产品时再加)。先把核心跑稳。
备选 · 适合后期

Stagehand(如果你想全 TS 栈)

Playwright + AI element identification

Stagehand = Playwright 控制层 + LLM 元素识别层。如果你后期发现电子税务局 改版太频繁、纯 selector 维护成本高,可以替换底层。它就是 page.act("点击批量下载按钮"),LLM 自动找到元素。但每一个 act 都是一次 LLM 调用, 所以仅用于不稳定的关键 1-2 步。

DECISION 02 · 模型选型

用哪个模型,什么时候用

Model selection — when, why, and how often

模型不应该在主循环里。模型只在两类时刻被调用: (a)视觉理解——截图过来,问"批量下载按钮在哪/页面什么状态"; (b)结构化抽取——HTML 片段过来,问"提取这张表里所有发票号"。

主力 · VISION
Sonnet 4.6
$3 / $15 per 1M tokens

OSWorld-Verified 72.5%——计算机 GUI 操作能力近乎 Opus,价格 1/5。 视觉看页面、定位元素、判断状态都靠它。 这是你的默认。

兜底 · 视觉硬骨头
Opus 4.7
$15 / $75 per 1M tokens

当 Sonnet 看不准时升一档。例如复杂表单状态判断、罕见弹窗。 仅作为 fallback 链路的最后一层,触发率应该 < 1%。

国内备用 · 合规场景
GLM-5.1
or DeepSeek
国内访问稳定

如果客户对"数据出境"敏感(尤其涉税数据),用国内模型替换。 视觉能力略弱,但对这种结构化页面够用, 你已经在评估 GLM 路线了。

不要用的:GPT-5.5 在 agent 上分数高,但价格贵 67%且这个场景里 它的优势(深度推理、长链规划)用不上。你买的是"看图说话"和"识表单",Sonnet 是甜蜜点。 GPT-5.5 留给 OpenClaw 的 Hermes/小诸葛 那种复杂规划场景。

调用频率估算(单次"拉一个客户一个月的发票"任务):

触发条件 频率 输入 tokens 输出 tokens 说明
主路径 selector 命中 ~95% 0 0 纯 Playwright 跑,不调模型
selector 失败 → 截图问 LLM ~4% ~2K(截图) ~200 Sonnet 视觉定位元素
未知弹窗 / 二次扫脸 ~1% ~2K ~100 判断 "是否需要人工接管"

按月 30 次任务、每任务 ~15 步、约 4% 触发 LLM 估算: 月 API 费用大约 ¥5–30。模型不是成本中心。

ARCHITECTURE · 系统架构

系统架构图

How the pieces fit together
① 人工登录入口(每天/每会话一次)
Human session bootstrap
打开 scripts/login.py → Playwright 以 headed 模式 启动 Chromium,用户在 GUI 完成账号密码 + 短信/扫脸 → 脚本检测到登录成功 → 保存 cookies 到 ./session/{企业税号}/ → 退出。 之后所有任务都用这个 session,直到过期。
▼
② 任务调度层
Scheduler
launchd 每天 18:00 触发 → 读 SQLite 任务表 → 派发到 worker。 支持手动 trigger(命令行 / 飞书指令)。无任务时不消耗资源。
▼
③ Worker · 确定性主循环
Deterministic core (Playwright)
按 selector 走 7 步:导航 → 查询 → 勾选 → 批量下载 → 轮询 → 解压 → 归档。 每一步包状态校验(expect()),失败立即抛出,不"乐观推进"。
▼
④ Vision Fallback(被动触发)
Visual fallback layer
主循环里某一步失败 → 截图发给 Sonnet 4.6 + 该步骤的"语义描述" (例如"找到'批量下载'按钮并点击")→ 模型返回坐标或新 selector → 主循环用 fallback 重试。3 次仍失败 → 升级到人工。
▼
⑤ 输出 · 归档 · 通知
Output, archival, notification
ZIP 解压 → 按客户/月份归到 ~/OpenClaw-Output/invoices/{客户}/{YYYY-MM}/ → 元数据写 SQLite → 飞书 webhook 发"今天拉到 38 张发票,合计 ¥XX,XXX"。 异常 → 高亮颜色告警,带截图链接。

骨架代码 · 三个核心文件

The three files that define the system

1. session.py · 持久化登录 session

# scripts/session.py — 人工登录一次,保存 session 到磁盘
from playwright.sync_api import sync_playwright
from pathlib import Path

def login_interactive(tax_id: str):
    user_data_dir = Path(f"./session/{tax_id}")
    user_data_dir.mkdir(parents=True, exist_ok=True)

    with sync_playwright() as p:
        ctx = p.chromium.launch_persistent_context(
            user_data_dir=str(user_data_dir),
            headless=False,           # 让人能看到、能操作
            viewport={"width": 1440, "height": 900},
        )
        page = ctx.new_page()
        page.goto("https://tpass.shanghai.chinatax.gov.cn:8443/")
        # 等待用户完成登录(检测跳转到主控台 URL)
        page.wait_for_url("**/etax.shanghai.chinatax.gov.cn/**", timeout=300_000)
        print("✓ 登录成功,session 已保存")
        ctx.close()

2. fetch_invoices.py · 主流程(简化版)

# scripts/fetch_invoices.py — 自动跑 7 步
from playwright.sync_api import sync_playwright, expect
from .vision_fallback import resolve_with_claude

def fetch(tax_id, date_from, date_to):
    with sync_playwright() as p:
        ctx = p.chromium.launch_persistent_context(
            user_data_dir=f"./session/{tax_id}",
            headless=False,    # 保持 headed,免触发风控
            accept_downloads=True,
        )
        page = ctx.new_page()
        page.goto("https://etax.shanghai.chinatax.gov.cn/...")

        # 检测 session 是否还活着
        if page.url.startswith("https://tpass."):
            raise SessionExpired("需要重新登录")

        # 步骤 1: 导航到全量发票查询
        page.click("text=我要办税")
        page.click("text=税务数字账户")
        # ... 继续到全量发票查询页

        # 步骤 2: 填查询条件
        page.fill("input[placeholder*='开票日期(起)']", date_from)
        page.fill("input[placeholder*='开票日期(止)']", date_to)
        page.click("button:has-text('查询')")

        # 步骤 3: 全选 + 批量下载(关键步骤,加 try-catch + vision fallback)
        try:
            page.click("th input[type=checkbox]")
            page.click("button:has-text('下载')")
        except Exception:
            # selector 失效 → 截图问 Claude
            action = resolve_with_claude(page, "点击批量下载按钮")
            action.execute(page)

        # 步骤 4: 选格式
        page.click("label:has-text('OFD')")
        page.click("button:has-text('确认')")

        # 步骤 5: 检测是否触发二次扫脸
        if page.locator("text=扫脸认证").is_visible(timeout=3000):
            notify_feishu(f"⚠ {tax_id} 触发二次扫脸,请手动完成")
            page.wait_for_selector("text=扫脸认证", state="hidden", timeout=180_000)

        # 步骤 6: 轮询 ZIP
        zip_path = poll_export_progress(page, ctx, timeout=600)
        ctx.close()
        return zip_path

3. vision_fallback.py · 模型兜底

# scripts/vision_fallback.py — 视觉兜底,仅在 selector 失败时调用
import base64, anthropic
from playwright.sync_api import Page

client = anthropic.Anthropic()

def resolve_with_claude(page: Page, intent: str) -> Action:
    screenshot = page.screenshot()
    img_b64 = base64.b64encode(screenshot).decode()

    msg = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=300,
        messages=[{
            "role": "user",
            "content": [
                {"type": "image", "source": {
                    "type": "base64", "media_type": "image/png", "data": img_b64
                }},
                {"type": "text", "text": f"""
页面截图如上。我要完成动作: {intent}。
请返回 JSON: {{"action": "click"|"fill", "selector": "...", "value"?: "..."}}
selector 优先用 text=... / role=... 这种语义化形式。
"""}
            ]
        }]
    )
    return Action.parse(msg.content[0].text)

为什么不用 Computer Use API?它会让 Claude 直接控制鼠标点坐标, 但坐标比 selector 更脆弱。让 Claude 返回"语义化 selector",由 Playwright 执行—— 这样兜底也是"软"的,失败仍可降级。

PITFALLS · 关键避坑

5 个新手坑

Five mistakes that will cost you a week each

① 不要用 headless 模式。政务系统的反爬有时会检测 headless browser (navigator.webdriver、缺失插件等)。用 headed + persistent context, 看起来就是真人在用 Chromium。Mac mini 上可以"窗口最小化但不 headless"。

② 不要在登录页做任何自动化。登录交给真人。脚本只在登录后接管。 这是合规边界,也是技术边界(扫脸/短信本来就过不去)。

③ 不要相信"刚加载完"。电子税务局是 SPA,大量 AJAX。 每个交互后用 page.wait_for_load_state("networkidle") 或者更好的 expect(locator).to_be_visible(),不要 time.sleep(2)。

④ 不要把 session 目录提交到 Git。cookies 里有完整的 access token, 泄露 = 别人能用你的身份办税。.gitignore 加 session/, 而且本地目录要 chmod 700。你之前有过凭证泄露经历,这一条尤其重视。

⑤ 不要一上来做"多线程并发"。电子税务局一个账号同时多会话会被风控 踢下线。每个税号串行跑。不同税号可以并行,但每个 Mac 进程独立、独立 Chromium 实例。

RECOMMENDATION · 我的建议

对你这个具体场景的判断

My take, given your background

基于你已有的背景——Python/Node 都熟、Mac mini 已部署、有 ESP32 / OAK-D 这种自己造轮子的偏好、 而且这套东西大概率最终会变成给 Accenture/Publicis SSC 客户的咨询交付物:

我的建议是不要走 agent framework 这条路。 Browser-Use / LangGraph 看起来"先进",但对一个单一已知流程的任务, 它们是反生产力的——每次跑都过 LLM,慢、贵、不可调试。

Playwright + 极薄的 Claude vision 兜底,代码不超过 600 行, 6 周可上生产。这个东西的真正价值不在"用了什么 framework",而在 "7 步流程的每一步都被你 selector + vision 双重锁定"。 这是你的护城河,不是 framework 选型。

如果未来要演化成产品给客户用,在这套核心之上再叠一层"任务编排 + 多租户管理 + Web UI", 那时候再考虑要不要引入 LangGraph 之类——但记住,业务逻辑还是那 600 行 Playwright, 不要重写。

最后,这个项目还有一个隐藏价值:它是你的"AI Agent 工程化"咨询包的活案例。 给 Accenture 讲"会用→会做→会造"时,这就是一个具体的"会造"案例。 所以把开发日记 + 踩坑记录留下来,以后是高价值素材。
